# Changelog

## 0.5.3

A correctness and security release answering a second audit of 0.5.2, again written by an AI agent instructed to review the package from the position of an Auki Labs engineer (Unity/C#) building a rules manager on it. Spec stays **`robot-domain-rules/3`**: no format or fingerprint changes; each behaviour change corrects something 0.5.2 did against the spec's own text and is listed as an erratum in SPEC.md § 11. Every fix below has a conformance case or core test that fails on 0.5.2 (commit `94ca4e7`) and passes here: 40 of the 261 conformance cases fail against the 0.5.2 build — 23 for the behaviours named below, 17 plan cases only because a plan evaluation now carries `approvalsUsed`.

### Fixed — critical (audit § 4, in the audit's order)

- **Forged-approval bypass closed** (audit item 1). 0.5.2's `withVerified` re-verified only when `signature` was a string, so an object with the right bound fields, `verified: true` and no signature cleared a wait on a trusted-keys rulebook through both `evaluateDomainAction` and `verifyAndEvaluate`. Now nothing in request data can assert verification: a `verified` member is ignored wherever it arrives; `verifyApproval` returns a **verified handle** — the very object it returns, registered by identity in a private `WeakSet` (`src/verified.ts`) — and under `trustedKeys` the evaluator clears a wait only for that object. A copy, a JSON round trip, or a hand-built object with the same fields is not it. The pure `evaluateDomainAction` on a trusted-keys rulebook therefore never clears a wait from request data and its reason says to use `verifyAndEvaluate`. Cases `approvals-unsigned-verified-flag-clears-nothing` (pure), `approvals-unsigned-verified-flag-clears-nothing-via-trusted-layer`, `approvals-bogus-signature-does-not-clear`, `approvals-forged-with-flag-does-not-clear`, `approvals-evaluate-alone-never-clears`; the trusted-path cases are now judged through `verifyAndEvaluate` (new conformance expectation `verifiedDecision` / `verifiedPlan`). SPEC.md § 9.3, § 14 "Verified handles".
- **One single-use approval cleared every plan step** (item 2). A plan now consumes approvals step by step: the nonce a step spends is in the consumed set every later step sees; `approvalsUsed` is reported at plan level (new, required member of a plan evaluation). Three steps behind one wait with one nonce: ALLOW, PAUSE, PAUSE. Cases `approvals-plan-consumes-step-by-step`, `approvals-plan-pure-evaluator-never-clears`. SPEC.md § 12.
- **The evaluator decided /1 and /2 rulebooks** (item 3). `evaluateDomainAction`, `evaluatePlan`, `verifyAndEvaluate(Plan)`, `matchingRules`, `checkRulebook`, `backtest` and `glassesZoneRules` now refuse a rulebook of another format with validation's exact message (`src/version.ts`): a decision-shaped BLOCK with ruleId `rulebook_version` (never a throw) from the evaluators, a `DomainRulesError` from the check and the backtest. A `/2` approval is refused by name with or without `trustedKeys` (0.5.2 took it as a plain approval). Cases `versions-*-refused-by-evaluator`, `versions-v2-rulebook-refused-by-plan`, `approvals-v2-approval-refused-without-keys`.
- **Integrity of derived content** (item 4). `validateRulebook` re-derives the area role-limit never rules from `areas[].allowRoles/denyRoles` and the findings from the rules, and compares: a rulebook with a derived rule stripped, altered or impersonated, or with findings emptied, downgraded or carrying an invalid witness, is invalid even with a recomputed fingerprint; reworded messages are fine. BOUNDARY.md now says exactly what validation guarantees and what only a pinned signature does. New file `conformance/integrity.json` (7 cases). SPEC.md § 2.2.
- **Plan clock offset** (item 5). `startTime` defaults to the wall-clock `HH:MM` written in `now`, in its own offset (`21:00-05:00` is 21:00 on site), not the UTC time of day. Cases `plan-clock-starts-at-the-wall-clock-of-now-west` / `-east`.

### Fixed — correctness

- **A selector that matches nothing is a finding** (item 6). New finding kind `unmatched_selector` (warning, certain, one rule, no witness) for a tag no declared thing carries, a kind no role or action has, or a selector emptied by its exclusions; tags match exactly, case included, and the message names a case-only near miss (`tag:staff-only` when the area carries `Staff-only`). Cases `p7-unmatched-selector-is-a-finding`, `p7-unmatched-entry-in-a-wider-selector`, `p7-exclusion-that-empties-a-selector`. SPEC.md § 7, § 7.6.
- **Several approvals per request** (item 7). `facts.approvedBy` may be a list; each approval clears at most one wait, so two waits need two approvals and one approval listed twice clears one. The glasses bridge maps every approval wait to `blocked` under `trustedKeys` (an on-device confirmation is not a signed approval). Cases `approvals-two-waits-need-two-approvals`, `approvals-list-each-clears-one-wait`, `approvals-list-one-approval-cannot-clear-two-waits`; core test for the bridge.
- **The drafter** (item 8). `ready` is renamed `confidentDraft` (`ready` kept as a deprecated alias with the same value until 0.6); it now also requires every word placed and confidence ≥ 0.6, and is the drafter's confidence in its reading, never a safety claim. The drafter drafts nothing — instead of a rule on everything — for an exception word (unless, except, but), a comparison it did not turn into a limit ("faster than the staff"), a "while"/"until" it could not read as a condition, or a "no ..." whose verb is not a declared action ("no scanning", "no dancing"). "Robots may not go faster than 1 m/s" is now a 1 m/s limit on movement (0.5.2: deny every action). "At most 2 robots in aisle 5" with a count fact binds the entering actions only (those with a `move` effect, else those tagged `movement`), so robots inside can act and leave. The switchboard shows unmatched words and notes first and asks the person to tick that they read the draft before confirming. Core tests for the four audit sentences.
- **`deepFreeze` reaches inside already-frozen parts** (item 9), and template rules are copied on compile, so two rulebooks from one template share no mutable `limits`. Core test.
- **Smaller** (item 10): `finalArea` after a `plan_area_continuity` refusal is where the earlier steps left the participant; `evaluatePlan` never throws on NaN/Infinity (the plan digest is taken over the plan as JSON); years 0000–0099 parse literally; sub-millisecond fractions are truncated to the millisecond, stated in SPEC.md § 1 with cases `approvals-sub-millisecond-*`; `canonicalJson` refuses lone surrogates and non-JSON values (functions, symbols, bigints) with a clear error; `signApproval` requires `expiresAt` later than `issuedAt`; `SEVERITY` and `hhmm` are defined once (`vocabulary.ts`); `requestDigest` is removed (it bound nothing; SPEC.md § 8.3 says so); the 0.2 input shape stays as deprecated authoring convenience that compiles to a `/3` rulebook (removed in 0.6) — consistent with refusing `/1`–`/2` artifacts, which it is not one of.
- **Conflict-check performance** (item 11). The site's role lists and unconditional never rules are computed once per check, covered areas are cached per (role, action), and the enumeration exits at the first reachable triple. The audit's case (20 roles, 40 actions, 40 areas, 120 rules): narrow selectors 3 ms → 2 ms; wide selectors **5,439 ms → 251 ms** (0.5.1, which did no reachability filtering and reported 2,973 findings including unreachable ones: 227 ms on the same machine).
- **Z3 sees reachability** (item 12). The cross-check's rulebooks now have three roles with different action lists, `who` selectors, never rules (some with conditions that can never fail), and every outcome; Z3 proves on its own which never rules are unconditional and both sides apply the same law (role lists action; no other unconditional never rule covers). A never rule whose conditions cover every value is now treated as unconditional by the checker too (`p7-always-true-never-rule-is-unconditional`). 341 rulebooks, 2,046 pairs (241 overlapping on facts but unreachable), 122 unconditional never rules, 796 witnesses.

### Spec and conformance (C# port readiness)

- SPEC.md § 14 rewritten: the per-language number advice was wrong (.NET `"R"` writes `1E+15`, Rust `{}` never uses exponents, Python `repr` switches at 1e16/1e-5); a real ECMAScript `Number::toString` serialiser is required, with JCS libraries named per language; vectors for `-0`, `5e-324`, `1e21` vs `1e20`, `1e-7` vs `1e-6`, 2^53+1, 0.1+0.2, the largest double (`fp-number-edges`); "hash the object as received, every member including unknown ones"; ordinal (UTF-16 code unit) key sort; lone-surrogate refusal; verified-handle type; Unity `JsonUtility` cannot model string-or-array selectors (use Newtonsoft or System.Text.Json); BouncyCastle for Ed25519 under IL2CPP (item 13).
- Witness judging: a port's `matches` must return exactly the reference's recorded `witnessMatches` on every reference witness, so "return every rule" fails; `ruleIds` must equal the expected pair (item 13). `client: true` marks the 205 cases a client must pass; `run-node.mjs --client` runs them.
- Schemas (item 14): 51 negative cases in `validate-schemas.mjs` (each schema must reject them); `by` is disallowed on condition waits; `approvedBy` may be a list; `verified` is marked deprecated/ignored; `participant.id`'s rule (required only when an approval is needed) is documented on the schema and in SPEC.md § 4; plan evaluations carry `approvalsUsed`; `unmatched_selector` and one-rule `ruleIds` in the findings schema.

### Docs honesty (items 15–19)

- BOUNDARY.md: every row names what is literally proved now — the verified handle, one approval per wait and per step, refusal at every door, what validation guarantees versus what only a pinned signature does, and that without `trustedKeys` an approver's authority is self-declared (development only).
- KNOWN-GAPS.md: the line claiming a higher authority can grant an exception by writing a rule is gone (strictest-wins means it cannot; stated as a gap); the overlapping-areas snippet keeps every area's limits (min across areas), collects every area's approval requests and traces, and a PAUSE in one area no longer drops another's limits; the SDK/mobile semantic-volume variant is listed as not supported; the drafter's limits restated.
- The harness adapter accepts every UUID form Rust's `uuid` crate accepts (hyphenated, simple, braced, `urn:uuid:`), judging uniqueness on the hex (item 17).
- RELATED-WORK.md: Cedar's decision rule is the same forbid-wins as this engine's — the difference is the ranked authority label used to classify conflicts at authoring time; Cedar's missing-attribute behaviour stated neutrally (an erroring policy is skipped and reported; default deny); RoboGuard's conflicts cell is plan-versus-specification; Open-RMF dispatches tasks and has no permission or authority layer; ASIMOV is a benchmark and a constitution-generation method, not a runtime (item 18).
- README says both audits were written by an AI agent role-playing an Auki engineer; counts updated (261 cases, 205 client, Z3 figures); PRINCIPLES "In code" links updated (`confidentDraft`, `integrity.json`, `versions.json`) (item 19).

### Changed

- Plan evaluation gains the required member `approvalsUsed`. `verifyApproval`'s returned approval no longer carries `verified: true` (it is the handle; `isVerified(x)` is exported). `Finding.ruleIds` may have one entry (`unmatched_selector`). `RuleDraft.confidentDraft` and `ParsedDraft.confidentDraft` (with `ready` deprecated). New exports: `RULEBOOK_FORMAT`, `RULEBOOK_VERSION_CHECK`, `rulebookVersionProblem`, `versionRefusal`, `isVerified`, `SEVERITY`, `timeOfDay`. Removed: `requestDigest`.

## 0.5.2

A correctness release answering an independent audit written from the position of an Auki Labs engineer (Unity/C#) building a rules manager on this package. Spec **`robot-domain-rules/3`**, rulebook format `neuroverse-domain-rules/3`, approval contract `robot-domain-rules-approval/3` (SPEC.md § 11 has the migration). Every fix below has a conformance case or core test that fails on 0.5.1 and passes here; 83 of the 231 conformance cases fail against the 0.5.1 build.

### Fixed (audit items)

- **The semantic-volumes surface threw on Auki's real data** (audit § 1). `examples/harness/volumes-to-areas.ts` now accepts exactly the collection `aukilabs/domain-harness` stores (`src/semantic_volumes.rs`, branch `develop`): `{ schema, frame, items: [{ id, title, description, semantic_type, center: [x,y,z], size: [x,y,z], yaw }] }`, validated as its Rust validates (unknown fields refused, UUID ids, limits on counts, lengths and numbers, schema and frame checked), `semantic_type` (default `region`) as the area's tag, `title` as its name. The `#tag` convention and the point-in-box helper are gone: membership is the spatial system's job, and the replay now takes area reports as events. The sample collection is in the real shape.
- **Multi-key limit loosening went unreported** (audit § 2a). Two limit rules are compared on every shared limit name; `{A:1,B:5}` under `{A:1,B:3}` is an `authority-override` for B; mixed cases (each tighter on a different limit) are a `limit_disagreement`. Case `p7-limits-compared-on-every-name`, `p7-mixed-limits-are-a-disagreement`.
- **A plan step could change area without moving** (audit § 2b). A step may name another area only if its action has a `move` effect; otherwise BLOCK `plan_area_continuity` (new built-in check, set by the evaluator). "check in x, check in y" + "ends in x" no longer passes. Cases `plan-step-area-without-move-is-refused`, `plan-step-area-restated-is-fine`; the old `plan-area-defaults-to-where-the-last-move-left-it` encoded the bug and now expects the refusal.
- **The glasses bridge loosened waits** (audit § 2c). A condition wait maps to `blocked` (the device cannot re-evaluate the condition); an approval wait maps to `confirm_each` only when the wearer may approve it (nobody named, or the wearer's role or tag, or an authority the wearer holds via the new `wearerAuthority` option) — otherwise `blocked`. Header rewritten to match. Core test.
- **History had no date** (audit § 2d). `history[].at` is an ISO 8601 timestamp with a date (no offset = UTC); windows are absolute time measured back from the new `request.now`; the `clock` member of a history condition is removed and rejected by name; an entry with a `/2` `"HH:MM"` time is `required_facts`. The backtest builds history from every earlier event (no day cut) and uses each event's `at` as the request's `now`; its `clock` option is removed. Cases `history-yesterday-is-not-today` (09:50 yesterday is not within 15 min of 10:00 today — 0.5.1 said it was), `history-window-crosses-midnight`, `history-offset-is-applied`, `history-now-missing-is-required-facts`, and the backtest cases.
- **Findings on clashes no lawful request can reach** (audit, smaller items). The check reports only pairs some reachable request matches: the role must list the action, and no unconditional never rule other than the pair may cover the triple. Cases `p7-unreachable-by-role-not-reported`, `p7-unreachable-behind-never-rule-not-reported`.
- **A subset test that always returned false for one shape** (`range ⊆ finite`): found by a property test against brute force on a small integer domain, now exact. Case `p7-range-inside-finite-set-is-covered`.
- **`evaluatePlan(undefined)` threw**: BLOCK `required_facts`, never a throw, for any non-object; SPEC.md § 15 lists exactly what throws. Case `plan-null-is-block`, core test.
- **A compiled rulebook aliased (and froze) the caller's `rule.source` object**: deep-copied now. Core test.
- **The drafter guessed** (audit § 3). "max 2 robots in aisle 5" was a 2 m/s speed cap at confidence 1.0; it is now a count — mapped to a declared count fact (`robotsInZone`-style, by name or synonym) as "wait while fact >= N" at lowered confidence, or refused with a note when the rulebook declares none. A bare number is never a speed without a unit or a speed word. "Don't let robots block the fire exit" is not ready: "block" is a verb the drafter does not model. `ready` now also needs confidence ≥ 0.5. README/AGENTS recommend the model-JSON-plus-validation path for real editors. Core tests for both examples.
- **Security claims made true** (audit § 4). Fingerprint: SHA-256 (FIPS 180-4, pure, synchronous, ~100 lines, standard vectors in `conformance/fingerprint.json`) over the UTF-8 bytes of RFC 8785 canonical JSON, 64 hex; findings excluded so two compilers agree. Approval: binds to rule id, rulebook fingerprint, participant id (required when an approval is needed), action, area, a unique nonce, `issuedAt` and a required `expiresAt`; the evaluator takes `now` from the caller and refuses expired, not-yet-valid, re-scoped, re-rulebooked and replayed (`consumedApprovals`) approvals, and reports `approvalsUsed` for the caller to record. An approval clears only its wait: a condition wait, a deny or a never rule on the current facts still decides (cases `approvals-facts-changed-condition-wait-still-holds`, `approvals-current-never-rule-still-blocks`, `approvals-current-deny-still-blocks`). `verifyAndEvaluate` / `verifyAndEvaluatePlan` are the recommended entries; the evaluator stays pure. BOUNDARY rows are each literally backed by named cases; "facts come from the harness, never from the requester" is integration rule #1, and the MCP example's `may_i` takes only `participant` and `action` and fills the rest from a stub harness.
- **Explicit version handling.** A `/1` or `/2` rulebook is refused at validation with a message naming its version and the migration; a `/2` approval (requestDigest, no nonce/expiry) is refused by `verifyApproval` and by the evaluator, by name; 16-hex fingerprints never verify. `conformance/versions.json`, `approvals-verify-v2-approval-refused`, `approvals-v2-approval-does-not-clear`.
- **Conformance quality for ports** (audit § 5). `compare.mjs` judges by deep semantic equality (key order irrelevant); every case input and reference output is validated against the JSON Schemas (`conformance/validate-schemas.mjs`, ajv as a devDependency; 507 validations, drift fixed in the schemas); SPEC.md § 14 "Porting notes" (JCS numbers, UTF-8 hashing, Ed25519 expectations, client vs authoring parts) and § 7's statement of why exact analysis is tractable and what "complete" covers.
- **CI** (audit § 6): `.github/workflows/ci.yml` — typecheck, core tests, conformance (vitest and `run-node.mjs`), schema validation, examples end to end, Cedar adapter tests, Z3 cross-check, site typecheck/tests/build; `concurrency: cancel-in-progress`; `permissions: contents: read`. README badge.
- **Docs honesty** (audit § 7): RELATED-WORK cites XACML delegation and AWS permission boundaries as prior art for tighten-only authority, corrects the Cedar "one law" row (Cedar is principal-agnostic; the difference is shipped participant semantics and two waits as outcomes), softens "the pattern the industry is settling on" to "one documented pattern", phrases RoboGuard's figure as support for guardrails outside the model, and says plainly that the ideas are known and the contribution is the combination and packaging. New `KNOWN-GAPS.md` (overlapping areas with the interim strictest-per-area rule and code, fact provenance and freshness, robot-to-robot coordination, authority not bound to identity, pinning and revocation, no persistence, replay depends on the caller's set). README: the implementation is a 0.x reference built quickly with AI assistance.

### Changed

- Spec `/3`, format `/3`: every fingerprint changes; every rulebook must be recompiled; approvals must be re-issued; `plan_area_continuity` is in `builtin`; `HistoryCondition.clock` and `BacktestOptions.clock` are gone; `ApprovalRequest` names `participantId`, `action`, `areaId` instead of `requestDigest`; `requestDigest` is now `fingerprint({ participantId, action, areaId })` and is a log key, not a binding.
- Conformance: 231 cases in 15 files (`versions.json` is new); `conformance/README.md` lists which cases a client needs.
- Package: `KNOWN-GAPS.md` and `conformance/validate-schemas.mjs` ship; `ajv` is a devDependency only; still zero runtime dependencies.

## 0.5.1

Test a rulebook against recorded activity before it goes live. Spec stays `robot-domain-rules/2`: § 13 is a new function over existing formats and changes no decision, finding, fingerprint or signature.

### Added

- **Backtest.** `backtest(rulebook, events, options?)`: replays a recorded log — `[{ at, request, outcome? }]` in time order — through a rulebook and reports what it *would have decided*: totals and counts by area, by role and by rule (ALLOW / LIMIT / PAUSE / BLOCK / missing facts, the five summing to the events); the rules that never fired; the rules and built-in checks that would have stalled work (PAUSE or BLOCK, most often first, with example timestamps); the findings that actually occurred (both rules matched a recorded request, by the same matching relation a witness is judged by); gaps (`unknown_action`, by action); the facts the log did not carry (by fact, via the new `missingFacts(rulebook, request)`); and, when the log records outcomes, where the rule and the record differ, without judging which is right. A rule that counts history gets the earlier events of the same participant on the same day of the log, unless the request brings its own. Pure, deterministic, no free text; every list has a defined order. `compareBacktests(baseline, proposed)` sets a current rulebook against a proposed one on the same log: newly blocked, newly allowed, other changes, and each rule's decided count before and after. SPEC.md § 13; `spec/backtest.schema.json`, `spec/backtest-report.schema.json`; `conformance/backtest.json` (13 cases, 194 in all); `compare.mjs` judges the report and the comparison deep-equal.
- **Sample week** (`examples/backtest/`): a clearly labelled synthetic week (189 events, not from a real store) at a grocery site with aisle 5, a `robotsInZone` count fact and the rule "at most two robots in aisle 5"; `backtest.ts` prints the report and the comparison with "at most three", and writes `sample-week.jsonl`.
- **Switchboard Test mode**: load the sample week (with its site) or import a JSON/JSONL log; the five-word summary, then the findings lists; "Compare with a proposed change" snapshots the rulebook as baseline, then any edit in the rulebook panel shows what would change. The log never goes in the link.
- Docs: README (engineer path step 4, operator path, roadmap: explaining *why* is out of scope), PRINCIPLES 5 "In code", RELATED-WORK row, AGENTS.md.

### Changed

- `evaluate.ts` names the facts behind a `required_facts` refusal internally (`missingFacts`); decisions, findings and fingerprints are unchanged for every existing rulebook (the 181 earlier conformance cases are byte-identical).

## 0.5.0

Whole-plan checking for AI planners, an exact conflict analysis cross-checked with Z3, a Cedar export, and a planner replay. Spec `robot-domain-rules/2`.

### Added

- **Whole plans.** `evaluatePlan(rulebook, plan)`: a planner proposes `{ participant, steps, initialFacts, history?, clock?, startTime?, stepDurationSeconds? }`; each step is decided with the single-action evaluator on the facts PROJECTED from the earlier steps' declared effects; the result is `{ status, steps (each with its decision and facts), planChecks, firstViolation?, approvalRequests, finalFacts, finalArea, planDigest, fingerprint }`. Nothing is projected past the first BLOCK; a PAUSE lists every approval the plan needs so a planner can collect them up front; a projected fact out of range is `required_facts`, never a clamp; a malformed plan is BLOCK, never a throw. SPEC.md § 12, `spec/plan.schema.json`, `spec/plan-evaluation.schema.json`.
- **Effects.** An action may declare `effects`: `{ op: 'set' | 'add' | 'subtract', fact, value }` or `{ op: 'move' }` (the participant is in the step's area afterwards). Validated against the declared facts. The grocery template's `enter_zone` and `dock` move, `manipulate` sets the new `carrying` fact and the new `place` action clears it; the warehouse template's `enter` and `dock` move. SPEC.md § 2.1.
- **Plan rules.** `rulebook.planRules`: `ends_in`, `ends_with`, `before` (optionally same area; the plan's `history` counts), `at_most`; each with `who`, `setBy`, `source`, `reason`; they can only reject and name the step where the plan breaks them. `DomainRulesBuilder.addPlanRule`, `validatePlanRule`. The grocery example gained `scan_before_restock` and `end_at_dock`, and a `no_carrying_through_checkout` rule. SPEC.md § 3.5.
- **History conditions.** A rule may carry `history: [{ actions, areas?, sameArea?, withinMinutes?, clock?, op, value }]` over `request.history` (`[{ action, areaId, at? }]`, caller-supplied). Windows use minute-of-day arithmetic on a declared time fact and wrap at midnight. A rule in scope that needs history and does not get it is `required_facts`. SPEC.md § 3.4.
- **Exact conflict analysis with witnesses.** `checkRulebook` is complete for the rule language: two rules are reported if and only if some request matches both, and every `certain` finding carries `witness`, a concrete request that triggers both rules (the smallest values in every overlap; SPEC.md § 7.4). Integer ranges are exact (closed on whole numbers; every-whole-number-excluded is empty). `certainty: 'possible'` now means only "a rule here has history conditions, which are not modelled"; it no longer means "partial overlap". `rulesOverlap(rulebook, idA, idB)` and `matchingRules(rulebook, request)` are exported. The switchboard's "Rules at odds" shows the witness with a "try it" button.
- **Z3 cross-check** (`test/z3-crosscheck.test.ts`, runs in `npm test`): hundreds of seeded rulebooks are encoded into the Z3 SMT solver and the checker must agree on every pair, and every witness must satisfy both formulas — 306 rulebooks, 1,836 pairs, 1,115 witnesses, ~6 s. `z3-solver` is a devDependency only.
- **Cedar export** (`adapters/cedar/`, its own package): `toCedar(rulebook) → { policies, schema, notExported, droppedByAuthority }`; authority resolved first; roles' action lists and allow rules → `permit`, deny and never rules → `forbid` with `when` clauses over `context`; LIMIT, both WAIT kinds, approvals, history and plan rules listed as not exported. Tested against `@cedar-policy/cedar-wasm` (strict validation; Cedar's decisions agree with ours on the exported subset for every example request).
- **Planner replay** (`examples/harness/plan-replay.ts`, `plans.jsonl` → `plan-decisions.jsonl`): v1 rejected at step 2, v2 pauses for one approval, Dana signs it (Ed25519, TEST ONLY key), v2 accepted. Readable transcript.
- **Switchboard Plan mode**: load a preset plan (the replay's v1 and v2 among them) or build one, step through it on projected facts, see the first violation, every step's decision, the plan rules, the approvals and where it ends. The mode and the plan travel in the link.
- Conformance: `plans.json` (19 cases) and `history.json` (14 cases); witnesses on every certain finding; `p7` gains every-shape and integer-exclusion cases; `compare.mjs` judges witnesses by validity through `impl.matches` and compares plan evaluations. 181 cases.
- Docs: SPEC.md § 2.1, § 3.4, § 3.5, § 7 (exact), § 7.4, § 7.5, § 12; PRINCIPLES.md (plans under 3, history under 4, exactness under 7); RELATED-WORK.md (whole-plan row, "layers, not competitors"); README roadmap ("rules that learn from evidence"; plan synthesis out of scope).

### Changed

- **Spec `robot-domain-rules/2`.** The exact analysis changed the certainty of some findings (`possible` → `certain` with a witness) and, through the `witness` member, the fingerprint of any rulebook that has findings. Decisions for existing rulebooks did not change. The rulebook `format` string stays `neuroverse-domain-rules/2`: every new member is optional and a rulebook without findings or plan rules keeps its fingerprint.
- Template actions now declare effects and the grocery template declares `carrying` and `place`, so rulebooks built from the templates (and the example fingerprints) changed. `inputFromRulebook` in the switchboard carries `planRules`.
- The published package adds `adapters/cedar/` (source, README, package.json) and the planner replay; still no runtime dependencies.

## 0.4.0

The release for engineers who will build their own: principles, a language-neutral spec with conformance tests, signed approvals, and a harness replay.

### Added

- **[PRINCIPLES.md](PRINCIPLES.md)** — nine principles for spaces shared by people, robots and AI, each enforced by named conformance cases. **[BOUNDARY.md](BOUNDARY.md)** — what this layer is and is not, what it trusts, the threat model, where each check belongs. **[RELATED-WORK.md](RELATED-WORK.md)** — how it compares with Cedar/AgentCore, ASIMOV, RoboGuard and Open-RMF.
- **[SPEC.md](SPEC.md)** (`robot-domain-rules/1`) — normative: every format, the decision algorithm as numbered pseudocode, the conflict analysis, authority semantics, canonical JSON and the fingerprint byte for byte, request digests, approvals. JSON Schemas (draft 2020-12) in `spec/`.
- **`conformance/`** — 144 language-neutral JSON cases grouped by principle, with shared rulebooks, Ed25519 test vectors under TEST ONLY keys, exact comparison rules (`README.md`), a framework-free runner (`run-node.mjs`) and the generator that produced them (`generate.ts`, intent stated by hand). The reference passes its own suite (`test/conformance.test.ts`).
- **Seeded soundness test** for the conflict analysis: every pair the checker calls disjoint is attacked with thousands of generated requests; none may match both rules.
- **Approvals as data, signed.** `ApprovalRequest` (returned as `decision.approvalRequests` on a PAUSE for approval: rule, required authority/role, `requestDigest`, `rulebookFingerprint`, reason), `SignedApproval`, `TrustedKey`. Ed25519 via the platform WebCrypto, no dependencies: `generateSigningKeys`, `publicKeyOf`, `signApproval`, `verifyApproval`, `signRulebook`, `verifyRulebookSignature`, `requestDigest`, `canonicalJson`. A rulebook may declare `trustedKeys`; then only an approval the caller verified (`verified: true`) and that is bound to this request's digest and this rulebook's fingerprint clears an approval wait. Without `trustedKeys` the plain `approvedBy` path still works (development only).
- **`validateRulebook(rulebook)`** — the problems, in plain words, with a rulebook received as JSON; what the spec calls rulebook validation.
- **Rules from agents and systems.** `source.kind` gains `agent` and `system`. A rule added by any author holding a declared authority goes in at that authority directly; `draftRuleFromText` / `parseRuleDraft` take `source` and `author` options and return `ready` (true when the draft has a declared authority and can be added as it is). The `grocery-store` template's authorities are now `law-and-safety` > `company` > `site-manager` > `staff` > `agent`.
- **`examples/harness/`** — `volumes-to-areas.ts` maps a semantic-volumes collection (the shape `aukilabs/domain-harness` describes; sample hand-written) onto rulebook areas, with an example-only `volumeAt`; `replay.ts` + `events.jsonl` replay an AI planner proposing tasks, poses and people counts, one signed approval and an emergency into an append-only `decisions.jsonl` and a summary. Deterministic.
- **`examples/mcp/`** — a ~100-line stdio MCP server (`may_i`, `explain_rulebook`) with its own `package.json`; the MCP SDK is a dependency there only.
- README restructured for two readers; "Where AI fits"; "Why not Cedar or OPA?". AGENTS.md leads with the principles and the conformance-case rule. The switchboard links PRINCIPLES and SPEC and shows the approval request a PAUSE returns.

### Changed

- **`engines.node` is `>=20`** (Ed25519 in WebCrypto). The core still has no runtime dependencies.
- The `grocery-store` template gained the `agent` authority, so rulebooks built from it (and the example fingerprints) changed. Decisions do not.
- The reason text of an approval that does not count under declared trusted keys says why (`… does not count here: …`). Reason texts are free-form and not part of the conformance contract.
- The published package now includes `PRINCIPLES.md`, `SPEC.md`, `BOUNDARY.md`, `RELATED-WORK.md`, `spec/` and `conformance/` (cases, runner, README); `examples/mcp` ships its source and `package.json` only.

## 0.3.0

### Changed

- **Generic model.** Nothing is hardcoded any more. A site declares its own kinds of participants, actions (each tagged with the kinds that may do it), areas (free tags), roles (actions, inheritance, tags), typed facts (`number`, `boolean`, `time`, `day`, `enum`, `string`; required or with a default), named limits (combined by MIN) and authorities. Every rule has one shape: `{ id, text, who, does, where, when, then, setBy, source, never? }`. `then` is `allow`, `limit`, `wait` (for approval or for a condition) or `deny` (with an optional `instead` hint). `compileDomain` and `evaluateDomainAction` keep their names.
- **Authority.** A rulebook declares an ordered list of authorities (templates default to `law-and-safety` > `company` > `site-manager` > `staff`). Every rule carries `setBy`. A lower authority may only tighten a higher one. `wait { for: 'approval', by }` names who may approve (an authority or higher, a role, or a role tag); `facts.approvedBy` may be `{ id, authority?, roleId? }` and only clears the wait if the approver holds it. Every check in a decision carries `setBy`.
- Rule IDs cited in decisions: `zone_declared` → `area_declared`, `unknown_actions` → `unknown_action`, `zone_role_limits` → `area_role_limits:<area>` (`:deny` for denyRoles), emergency glasses commands → `emergency_stop_commands`, `zone_speed_cap` → `zone_speed_cap:<zone>`. A `command_robot` request without `targetRobotId` is `required_facts`. `rulebook.policy` is gone (`answers` and `rules` carry the same information). `format` is `neuroverse-domain-rules/2`.

### Added

- **Templates** whose answers emit rules: `grocery-store` (the ten 0.2 questions, same decisions) and `warehouse` (aisle exclusivity, robots per aisle via a numeric fact, dock access). A site may pass its own `Template` or none.
- **Plain-text drafting**, deterministic: `draftRuleFromText(text, rulebook, { setBy })` matches common forms against the rulebook's own names and synonyms and returns `{ draft, confidence, unmatched, notes }`. Never adds a rule.
- **Drafting with the operator's own model**: `buildRuleDraftPrompt` and `parseRuleDraft`. No network calls in the package; the model never sets the authority.
- **Conflict detection**: `checkRulebook(input | rulebook)`, also run by `compileDomain` and returned as `rulebook.findings`. Kinds: `contradiction`, `authority-override`, `never_vs_rule`, `shadowed`, `duplicate`, `limit_disagreement`, `tightening`. Each finding has a severity, rule IDs, a certainty (`certain` / `possible`) and a plain-English message naming which rule wins and which never takes effect. Disjointness is sound: only claimed when provable. `compileDomain(input, { strict: true })` throws on conflicts.
- `renderDomainRules` now shows authorities, facts, limits, never rules, every rule as `who · does · where · when → answer` with who set it and where it came from, and the findings.
- `DomainRulesBuilder`: `fromTemplate`, `as`, `action`, `area`, `fact`, `limit`, `tags`, `authorities`, `otherwise`, `addRule`, `addRuleFromText`, `confirm`, `check`, `toInput`.
- Examples: `grocery-store.ts` (with two deliberately conflicting manager rules), `warehouse.ts`, `clinic.ts` (no template), `demo.ts` prints all three.
- 38 tests (the 20 from 0.2 ported, plus generic sites, every operator, overnight windows, each finding kind, soundness, authority, drafting, strict mode, 0.2 equivalence).

### Deprecated

- The 0.2 input shape `{ site: { domainId }, zones, roles, answers }`. Still accepted and translated through the `grocery-store` template; decides identically. Request fields `zoneId` and top-level `targetRobotId` are still accepted.

## 0.2.0

### Fixed

- Missing or invalid facts are never permission. A request without `peopleInZone`, with a bad `localTime`, a negative count, a non-number speed, or a malformed participant/zone/action now gives `BLOCK` with the new fixed rule `required_facts`, naming what is missing. Before, an absent `peopleInZone` read as an empty zone, and a bad `localTime` threw instead of deciding.
- Fundamental restrictions apply to every action. An unknown action approved under `unknown_actions: pause` now still faces the emergency, opening-hours, zone-kind, zone-role and people rules. Before, it returned early and was allowed during an emergency and after hours.

### Added

- Per-zone role limits: `allowRoles` and `denyRoles` on a zone, rule `zone_role_limits`. Checked at compile time (unknown role, role in both lists → `DomainRulesError`). Inheritance does not pass zone permission. Rendered by `renderDomainRules`.
- Compiled rule sets are deep-copied from the input and deep-frozen, so later edits to the input cannot change them and the fingerprint stays true.
- `verifyFingerprint(ruleSet)`: recompute and compare, for a rule set received as JSON.
- `isValidTime(value)` export.
- `emergency` is documented as the one fact with a default (absent = no emergency active).
- Example store gains a `restroom` zone limited to `cleaning_robot`, `staff`, `shopper`; the demo shows a restock robot blocked and the cleaning robot allowed. The example fingerprint changed accordingly.
- README describes the package as a governance core and adds "Who does what"; AGENTS.md mirrors the contract and new invariants.
